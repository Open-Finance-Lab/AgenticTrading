# Issue #148：历史资金曲线唯一性迁移设计

## 1. 背景

Nemotron 完整窗口实验重新使用固定 `run_id` 写入排行榜数据库后，`agent_runs` 中的成绩行被正确替换，但读取到的资金曲线包含新旧两组数据：

- `run_id`：`lb_nemotron_3_nano_30b_20260415_20260515`
- 曲线总记录数：644
- 不同时间戳数：161
- 每个时间戳存在 4 条记录
- 其中 483 条是旧的 10 万美元量级数据，161 条是新的 1 万美元量级数据

新建数据库时，`equity_timeseries` 表声明了 `UNIQUE(run_id, timestamp)`。但仓库中的历史数据库早于该约束，现有迁移代码没有为旧表补充唯一索引。因此，`INSERT OR REPLACE` 在旧数据库里找不到可冲突的唯一键，实际行为是不断追加。

这个问题不会改变本次运行在内存中计算并保存到 `agent_runs` 的收益指标，但会污染排行榜和回测接口读取的展示曲线。因此，必须先恢复曲线存储的一致性，才能继续评价 Issue #148 中 Nemotron 的真实表现。

## 2. 目标与边界

本次变更只修复 SQLite 历史数据库中的资金曲线唯一性：

1. 旧数据库打开时，按 `(run_id, timestamp)` 清理重复曲线点。
2. 每组重复记录保留 `id` 最大的一条，即最后写入的记录。
3. 为旧表建立 `(run_id, timestamp)` 唯一索引。
4. 以后相同回测重新写入同一时间点时，现有 `INSERT OR REPLACE` 能正确覆盖旧值。
5. 新建数据库和已经具备等价唯一约束的数据库保持原有行为。

本次不修改 Nemotron 配置、模型提示词、响应解析、交易算法、仓位管理、模拟成交、收益指标算法、排行榜 API 或其他数据表，也不清理或提交仓库中的实验数据库文件。

## 3. 方案选择

### 3.1 采用方案：历史数据迁移并建立唯一索引

在 `BacktestDatabase` 初始化过程中增加一个独立、严格的资金曲线迁移步骤。迁移先检查 `equity_timeseries` 是否已经存在覆盖 `(run_id, timestamp)` 的唯一约束；如果存在则直接返回。如果不存在，则在同一个事务中删除旧重复行并创建命名唯一索引。

该方案同时修复已有数据和未来写入行为，覆盖普通回测、排行榜回测及外部 Agent 回测等所有共用 `BacktestDatabase` 的入口。

### 3.2 未采用：仅在排行榜强制重跑前删除曲线

该方案改动较小，但只保护 `deploy_model_run()` 路径。普通回测或其他写入方在历史数据库上仍会继续产生重复点，数据库本身的不变量没有恢复。

### 3.3 未采用：只清理当前本地数据库

手工删除能够暂时修正当前展示，但其他开发者、部署环境和已有数据库仍然会遇到同一问题，也没有自动测试防止回归。

## 4. 架构与迁移流程

初始化顺序为：

```text
BacktestDatabase 打开数据库
        ↓
创建新安装所需的数据表
        ↓
执行现有字段和交易表迁移
        ↓
检查 equity_timeseries 的唯一约束
        ↓
已有等价唯一约束 ───────────────→ 完成
        ↓ 没有
按 run_id + timestamp 分组
每组只保留 MAX(id)
        ↓
创建 UNIQUE(run_id, timestamp) 索引
        ↓
提交事务并完成
```

唯一性迁移使用独立的内部方法，避免改变现有宽松迁移对其他历史字段的处理方式。唯一索引的检测必须检查索引是否为唯一索引，以及索引列是否按顺序恰好为 `run_id`、`timestamp`，不能只根据索引名称判断。

去重规则固定为保留 `MAX(id)`。`id` 是自增主键，因此它代表相同回测和时间戳最后写入数据库的版本。这正好符合 `--force` 重跑时用新曲线替换旧曲线的语义。

## 5. 写入与读取行为

迁移完成后，现有写入接口不需要改变调用方式：

- `insert_equity_point()` 写入已存在的 `(run_id, timestamp)` 时替换旧记录；
- `insert_equity_points()` 批量写入相同键时同样替换；
- `get_equity_curve()` 对每个时间戳最多返回一个点；
- 使用全新时间戳时继续正常追加。

本次不在读取层临时去重。读取层隐藏重复数据会让错误继续留在数据库中，并使不同查询得到不一致结果。

## 6. 事务与错误处理

删除重复行和创建唯一索引必须处于同一个 SQLite 事务中：

- 两步成功后才提交；
- 任意一步失败时整体回滚，不留下“已删除但未加保护”的半迁移状态；
- 唯一性迁移因**数据问题**失败时向调用方抛出异常，停止 `BacktestDatabase` 初始化；
- 不沿用现有普通迁移只打印 warning 后继续运行的行为，因为继续运行会让排行榜展示已知错误的数据。

**（评审修订）失败分类。** 上述硬失败只针对数据问题（`sqlite3.IntegrityError`、索引名被非唯一索引占用
导致创建后校验不通过）。`sqlite3.OperationalError`（`database is locked`）是另一类：

- 它是瞬时的——回测 CLI、Discord bot 或另一个 uvicorn 进程正持有写锁；
- `database.py` 末尾是模块级 `db = BacktestDatabase()`，在这里抛异常等于 `import dashboard.backend.database` 失败，应用完全无法启动；
- 相邻的既有迁移在同样条件下本来就是打印 warning 后继续。

因此对 `OperationalError` 用新连接重试一次（每次连接有独立的 busy timeout），仍失败则打印
`⚠️ equity_timeseries uniqueness migration deferred: ...` 并推迟到下次启动。所有 `equity_timeseries`
写入方本来就用 `INSERT OR REPLACE`，推迟一次不会比迁移存在之前更糟。

数据库文件本身不存在 `equity_timeseries` 表时，正常初始化会先创建该表及其唯一约束，因此不会进入清理分支。已经迁移成功的数据库再次启动时检测到等价唯一约束并跳过，保证迁移幂等。

## 7. 测试设计

自动测试全部使用临时 SQLite 数据库，不修改仓库中的 `dashboard/storage/data/backtest.db`。

1. 构造没有唯一约束的旧版 `equity_timeseries` 表，并为同一个 `(run_id, timestamp)` 插入多个不同值。
2. 在实现前运行该测试，证明当前代码会保留重复记录或缺少唯一约束。
3. 初始化 `BacktestDatabase` 后，确认每组只剩 `id` 最大的记录。
4. 通过 SQLite 索引信息确认迁移后存在覆盖 `(run_id, timestamp)` 的唯一约束。
5. 再次写入同一键，确认值被替换且记录数不增加。
6. 再次初始化同一数据库，确认迁移幂等且数据不再变化。
7. 新建数据库测试继续通过，证明新安装行为没有回归。
8. 运行数据库相关测试和后端测试，检查普通回测、排行榜及外部 Agent 共用写入路径没有受到影响。

真实数据验证使用实验数据库的临时副本。打开副本触发迁移后，Nemotron 完整窗口应从 644 条记录变为 161 条，且 161 个时间戳全部唯一。原始实验数据库保持未提交状态，不纳入代码提交。

## 8. 成功标准

- 任意数据库中，每个 `(run_id, timestamp)` 最多存在一条 `equity_timeseries` 记录；
- 历史重复数据自动保留最后写入版本；
- 同一 `run_id` 强制重跑后，曲线长度不会因为重复写入而增长；
- Nemotron 临时数据库副本的曲线从 644 点恢复为 161 个纯净点；
- 相关自动测试和后端回归测试通过；
- 提交中不包含 API Key、数据库二进制变化或与 Issue #148 无关的改动。

口语化地说，这次先把同一学生同一天的多张成绩单整理成最新一张，再给档案柜加一条硬规定：同一天只能放一张。这样以后重考是更新成绩，而不是把新旧成绩混在一起画曲线。
