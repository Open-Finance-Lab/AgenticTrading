# A Backtest You Can Watch Start and Run Twice — Design

**Follows:** [#474](https://github.com/Open-Finance-Lab/AgenticTrading/issues/474) (items 1, 2, 5 shipped or on `feat/474-backtest-timeout-outcome`), and the 2026-09-20 architecture diagnosis recorded in the session memory `backtest-latency-nondeterminism-diagnosis`.
**Scope:** `runtime_type="pipeline"` + `decision_source="llm"`, launched from `POST /backtest/run`. The hosted `ai_hedge_fund` runtime and the CLI-only paths are touched only where the same code runs.
**Status:** approved in brainstorming 2026-09-20. One decision changed after the code was read and is marked **⚠ changed**.
**Line references** in this document are against the code tree of `origin/main` as of 2026-09-20 (`ae0fdad7`), which `docs/backtest-speed-and-trust@c68076ac` — the working branch's tip — reproduces byte-for-byte outside `docs/`, the branch adding nothing but these three documents. **Resolve an anchor against `origin/main` or that tip, never against a local `main` you have not fetched.** The checkout these documents were written in has `main` at `924dffc2`, two commits and 19 files behind (`622716c3`, `ae0fdad7`), and that gap moves things this document depends on: `ae0fdad7` inserts two statements into `PostgresUserStore._init_schema`, so on that stale tree `users_postgres.py`'s `__init__` is at `:77` rather than `:78`, and the eleven-twin parent DDL total quoted below is 126 rather than 128. Re-deriving an anchor on the wrong tree is the failure this note exists to prevent, so `git fetch` first. Sequencing step 0 rebases `feat/474-backtest-timeout-outcome` onto `origin/main` and lands it; that branch rewrites `api/routers/backtests.py` and `frontend/app.js`, so every anchor into those two files moves when it does, by an amount the rebase decides and which nothing here can predict (the branch is not a descendant of this tree, so its current numbers are not the post-rebase ones either). The Track A plan executes on *that* tree and carries its own anchors. The two sets are deliberately not the same and neither should be "corrected" into the other — re-derive with grep instead.

## The three symptoms, and which this closes

A user launching the onboarding backtest today gets, in order:

1. **A dark start.** The card says "Starting backtest…" and nothing else until the first hourly bar has finished its whole pipeline. Behind that sentence the child cold-imports pandas and three SDKs, seven module-level store singletons are constructed as an import side effect, six of them Postgres twins that each run their schema DDL against Neon in `__init__`, Alpaca bars are fetched and aggregated with a Python `iterrows` loop (`domain/backtesting/bar_aggregation.py`), and then bar 1 runs every pipeline step. The only progress write in the engine is `_publish_live_progress` (`engine.py:588`), called only inside the bar loop (`:1621`). Nothing before that is visible, and nothing before that is measured.

   Six twins, not the four an earlier draft of this document named, and the number is derived rather than remembered — **Task 6 Step 8** of the Track A plan ships `count_child_ddl.py`, which imports the child's own module behind a stubbed pool and counts the statements each twin issued (Task 5's own preamble probe answers the different question of *which* singletons a child builds, and counts nothing): `PostgresBacktestDatabase` (`database_postgres.py:59`, 55 statements), `PostgresModelProviderStore` (`model_providers/repository_postgres.py:154`, 18), `PostgresAnalyticsStore` (`analytics/repository_postgres.py:195`, 16), `PostgresAgentStore` (`agents/repository_postgres.py:35`, 14), `PostgresCreditsStore` (`credits/repository_postgres.py:662`, 3) and `BrokerConnectionStorePostgres` (`brokers/repository_postgres.py:70`, 1) — **107 statements over six pooled checkouts** before a bar is read. Six and not seven because seven store singletons are built (below) and only six of them have a Postgres twin: the seventh, `domain/runs`' `RunStore`, has no `*_postgres.py` sibling at all — protocol runs are SQLite by design, and its DDL is a local file rather than a Neon round trip. A warm schema does not shrink that: 72 of the 77 `ALTER`s are `ADD COLUMN IF NOT EXISTS`, and the remaining five are `DROP CONSTRAINT IF EXISTS` / `ADD CONSTRAINT` / `ALTER COLUMN … DROP NOT NULL` migrations, so all 107 round-trip whether or not the change has already been applied. Nor is it six *connections*: `db_pool.get_pool` caches one pool per URL at `min_size=0` — `AGENT_RUNS_DATABASE_URL` for run history, `CONTENT_DATABASE_URL` for agents, `USERS_DATABASE_URL` for the other four — so the first store on each URL pays the cold handshake and the rest reuse it.
2. **A long run.** Wall-clock is bars × decision steps × one blocking model call. That floor is architectural and out of scope here.
3. **Results that do not reproduce.** The pipeline request builder `_create_pipeline_response` (`infrastructure/llm/pipeline_runner.py:505`) sends `model`, `max_tokens`, `system` and `messages`, and nothing else. No temperature, no reasoning effort. The worker client already accepts and validates both (`execution/client.py:102-122`) and every adapter forwards temperature (`adapters/anthropic.py:85`, `gemini.py:60`, `openai.py:113`). The engine passes neither on either branch (`engine.py:1483`). Each bar's prompt embeds the previous bar's sampled action, so a 49-bar run is 49 dependent samples with no re-anchoring.

This design closes **1** (the start is visible, and cheaper where the cost is waste) and **3** (sampling is pinned, recorded, and shown). It does not close **2**; see *Out of scope*.

## What the user sees afterwards

- Within one poll tick of the child reaching `load_data` **both running surfaces name a phase with an elapsed clock, in two different registers, from two tables.** The **Backtest panel** prints the server's sentence — `/backtest/status`'s `message`, built from the phase table in `backtests.py` and rendered by `updateBacktestRunProgress` (`app.js:8198`, fed `status.message` at `:8628`): *Loading market data…*, *Calculating indicators…*, *Waiting on the first model decision…*, the existing *Backtest running… step k/N*, then *Saving results…*. The **My Agents card** prints its own short label from a client-side table, through `deriveRunningProgress`'s `stepLabel`/`detail` (`app.js:8058`, rendered at `:1324`/`:1330` and patched at `:6254`/`:6257`): *Loading market data*, *Calculating indicators*, *Waiting on first decision*, *Saving results*. Two tables on purpose — a card line is not a status sentence, and only the phase *name* is the contract between them. Off the shared helper the panel takes `eta` and `notice` and nothing else (`app.js:8223`), so the two can differ in wording without diverging in fact. The one crossover is `attachToLiveBacktest` (`app.js:8382`), the deep-link / reload-mid-run path, which ignores `status.message` and writes its own — it borrows the card's short label for the single tick before the 1 s poller replaces it with the server sentence.
- ***Saving results…* outranks the step count on both surfaces, and that is a user-visible change.** `saving` is the one phase published *after* the bar loop, so it arrives carrying the loop's final numbers rather than zeros (see the progress contract below). That tail is not a moment: `saving` is the **last** phase the child ever writes, so it stands until the process exits, and what runs under it is the rest of `run_agent_backtest` plus two whole baseline simulations `main()` calls after it returns — `run_buyhold_baseline` (`engine.py:1800`) and `run_djia_baseline` (`:1888`), from `backtest_hourly_agent.py:513` and `:522` — each with its own `db.insert_run(` (`:1859`, `:1941`). A count-first rule would freeze the panel on *step 49/49 (99%)* for all of it, beside a run that is plainly still working, and it would make the *Saving results…* row unreachable: a sentence in a table nothing can ever print, which is the same defect the `starting` guards exist to prevent. So the phase wins over the step count for `saving` only; every other phase still yields to a real step.
- The bar count reaches the My Agents card as a `0/N` step label as soon as it is known, before the first model call; the **bar itself stays indeterminate** until a real step, because `determinate` requires `step > 0` (`app.js:8005`) and the renderer paints a determinate bar by toggling `is-determinate` and setting an explicit width (`app.js:6299-6303`) — a determinate bar at step 0 is an empty track with the indeterminate sweep switched off, which reads as broken rather than as starting.
- **Before `load_data`, the card says exactly what it says today, and this design does not change that.** The parent builds the command; the interpreter starts; the script's module-level imports pull in pandas, three SDKs and 7 of the repo's 12 module-level store singletons (`database.py:1164`, `domain/agents/repository.py:812`, `domain/analytics/repository.py:672`, `domain/brokers/repository.py:299`, `domain/credits/repository.py:3338`, `domain/model_providers/repository.py:1079`, `domain/runs/repository.py:469` — only `db` is imported by the script itself, at `backtest_hourly_agent.py:40`; the other six are side effects of the two service imports at `:177-178`, and only two of them, `analytics_store` and `run_store`, need the analytics chain those imports pull in. *Where the start is waste* traces both routes); only then does `main()` run and construct `HourlyBacktester`. Every one of those costs is paid before an engine method exists to publish anything, so the card keeps *Starting backtest…* and, past two minutes, *Still starting up — no steps reported after Nm*. That window is **measured, not narrated** — see *Why `starting` is measured and not narrated* below. Attacking its cost (the DDL skip in Track A, and deferring the store imports out of the child's module scope, which this release does not do) is the only thing that shortens it; a sentence would not.
- The results panel carries a **Sampling** row, one state per *shape* of recorded request — five as the policy table below stands, and the count moves with that table, so nothing downstream should assert a number:
  - *Pinned · temperature 0* — the temperature-only rows.
  - *Pinned · reasoning effort low (no temperature sent)* — the note explains the **absence** and makes no claim about the model. The one catalog row with this shape is `openai/gpt-5.5`, which *rejects* a non-default temperature rather than ignoring one, so the obvious wording ("this model ignores temperature") would be false on the only run that can render it.
  - *Pinned · temperature 0 · reasoning effort low* — the both-values rows, DeepSeek V4 Pro and Qwen3.7 Plus. No caveat, even though those two do ignore temperature while thinking: the row reports the request, and this formatter reads the shape of a recorded request rather than the catalog, so any caveat here would be asserted of a future both-set row for a model that honours the value.
  - *Provider default* — an LLM run that pinned nothing, because the route was not resolved from the catalog.
  - *Not recorded* — runs written before this shipped.
- The same configuration run three times produces curves that diverge later and by less. The number is measured and recorded in the plan, not promised on the card. **The card never says "deterministic".** Providers are not deterministic at temperature 0, mixture-of-experts models least of all; what is pinned is the request, and what is shown is exactly that.

## Track A — the start is visible, then cheaper

### Progress contract

The child already owns the progress file (`--progress-file`, rewritten whole on every step; the reader in `_read_progress_file` tolerates a torn write by returning `None`). Track A adds a second writer beside `_publish_live_progress`, `publish_phase(name)`, and three fields to the payload:

| field | type | meaning |
|---|---|---|
| `phase` | `"loading_bars" \| "indicators" \| "first_decision" \| "running" \| "saving"` | the phase in progress. Never `"starting"` — nothing can write it; see below |
| `phase_started_at` | float, epoch seconds | when the current phase began |
| `phases` | list of `{name, started_at, ended_at}` | every finished phase, in order, `"starting"` first — and that first entry alone carries three more keys (`child_entered_at`, `imports_done_at`, `schema_init_seconds`), for the reason given under *Where the start is waste* |

`step` and `total_steps` keep their meaning, but the rule for a phase payload has **two halves, split on the bar loop** — one skeleton before it, carry-forward after it.

**Before the loop**, a phase write carries `step: 0`, `equity_curve: []` and `total_steps: 0` until the bars have been counted — which happens later than "the data is loaded" suggests. `load_data` fetches and builds the dataset, but the *decision-bar count* does not exist until `all_timestamps` has been filtered to market hours and trimmed to the window inside `run_agent_backtest` (`total_steps = len(all_timestamps)`, `engine.py:1423`), two phases after `loading_bars`. So the real `total_steps` rides the `first_decision` write, and the `loading_bars` and `indicators` payloads honestly say `0` rather than guessing from the source bars. That is still "as soon as it is known, before the first model call" — the bullet above and the Testing line below both already say it that way; only this sentence had it at the wrong phase boundary. The frontend's `deriveRunningProgress` already requires `step > 0` before it anchors an ETA (`app.js:8005`), and `updateLiveBacktestChart` / `updateLiveTradingLog` return early on a payload with no curve or no orders (`app.js:8830`, `:9203`), so **these pre-loop payloads** are safe for every existing reader.

**After the loop**, that same skeleton is destructive, and exactly one phase is written there: `saving` goes immediately before the agent's `db.insert_run(` (`engine.py:1748`), which is past the last `_publish_live_progress` (`:1621`, inside the loop at `:1458`). A post-loop write therefore **carries the last published payload forward and changes only the phase fields and the bar count** — the file never says less than it last said. The reader-safety argument above does not extend to it: the Backtest panel's bar computes its percentage straight off this file's raw `step`/`total_steps` (`app.js:8600`) and never passes through the My Agents fold, so a `step: 0` write at that moment snaps the bar from 99% to 0 and *no* frontend guard can reach it. Track A implements both halves in one `publish_phase` and pins the post-loop half with its own regression cases.

`_publish_live_progress` sets `phase: "running"` and appends the finished pre-loop phases so the history survives the first step.

Phases are marked by the engine, not the script: `load_data` marks `loading_bars`, `calculate_indicators` marks `indicators`, `run_agent_backtest` marks `first_decision` once it has counted the bars, the first `_publish_live_progress` flips it to `running`, and `run_agent_backtest` marks `saving` immediately before the agent's own `db.insert_run(` (`engine.py:1748`, the first of three — the two later calls write baselines; there is no `save` method to hang it on). **Every transition also prints one line to stdout**, emitted by the same writer from the same clock that writes the payload. It is the engine and not `main()` for two reasons: `main()` cannot see `first_decision` open and close inside `run_agent_backtest`, so a `main()` implementation would print a strictly worse set of phases than this sentence promises; and a second elapsed clock in the script is the two-owners pattern this repo already documents. `main()` therefore keeps exactly the three numbered banners it has (`1️⃣`/`2️⃣`/`3️⃣`, `backtest_hourly_agent.py:473-492`), which carry no times and are not phase names. The stdout copy is not a convenience: the parent unlinks the progress file the moment the run ends, so `phases[]` can only be read by racing a live poll, while the child's stdout is captured head+tail (`SUBPROCESS_LOG_HEAD_CHARS`/`SUBPROCESS_LOG_TAIL_CHARS`, 32k each, `backtests.py:2163-2164`) and dumped into the parent's log under `=== BACKTEST SCRIPT OUTPUT ===` (`:1568`), where it keeps. It is also the only phase record the paths with no progress file have at all: a CLI run, the external-run session, the algo service.

**Why `starting` is measured and not narrated.** `publish_phase("loading_bars")` is the *first* write to the progress file, and it is also the earliest write that can exist: everything before it runs at module import, before `HourlyBacktester` is constructed. `starting` therefore never appears as a live `phase` value — it is the **name of the gap**, closed retroactively into `phases[]` by that first write, against the launch clock the parent stamps once and spends on both the run slot's `started_at` and the child's `--launched-at`. Two earlier writers were considered and refused. A parent write at `Popen` would stamp the file before the child exists, which destroys the one fact file-absence currently proves — that the child got as far as running — and makes a child that died in its imports indistinguishable from one that is working; that is the failure shape *Fail-closed is not fail-visible* in `CLAUDE.md` describes, and it would also re-route `resolveRunningNotice` (`app.js:7909`) off *Still starting up — no steps reported after Nm*, which is true during imports, onto *No progress for Nm — long model steps can do this*, which is false before any model call. A stdlib-only writer in the script's bootstrap block (above the heavy imports, the only in-child placement that is early enough — `main()` is at `backtest_hourly_agent.py:185`, below them) preserves that signal but needs a second argv parser that will drift from argparse, and the only sentence it can deliver is *Starting backtest…*, which `app.js:10358` already paints optimistically before the POST returns. A progress file whose sole content is "I have not started" is worse than no progress file. If a genuinely earlier writer is ever built — in the same commit as something new for it to say — the sentence and the label go in with it; until then their absence is the honest state and is pinned by tests. What the script *does* stamp in its preamble is a pair of plain module constants, `CHILD_ENTERED_AT` and `IMPORTS_DONE_AT`, which need no parser and write no file; they are handed to the engine and land in the `starting` record described below.

### What the reader says

`/backtest/status` (`api/routers/backtests.py:3321-3328`) currently derives its sentence from `step/total_steps` and otherwise falls back to *Backtest is running… (multi-step agent pipeline; may take several minutes)*. It gains one phase → sentence table, and the **Backtest panel** renders that sentence verbatim beside its existing elapsed clock — the My Agents card does not, and draws its own short label instead (see *What the user sees afterwards*). One of the table's entries, `saving`, is checked **before** the step count rather than after it, for the reason given there. The message is built server-side for the same reason the staleness age is: both ends of the phase clock are read in one process.

### Where the start is waste

Two costs are pure waste and are removed; the rest is measured first.

**Schema DDL in the child.** The parent runs every store's DDL at import, so by the time it spawns a child the schema exists. The parent sets `ATL_BACKTEST_WORKER=1` in the child's environment (the `env` copy at `backtests.py:1480`, inside `run_backtest_background` at `:1381`), and every Postgres twin that owns a schema routes its constructor's DDL through **one helper**, `db_url.init_schema_unless_worker(label, init_schema)`, which either skips it and prints `<store> backend: schema init skipped (backtest worker)`, or runs it, times it into a process accumulator and prints `<store> backend: schema init 0.42s`.

**All eleven twins, not the six a child imports today.** Which stores a child constructs is an accident of the import graph, and the accident arrives by **two independent routes**. Both were traced by execution, not by reading:

- **The child's own module-level imports.** `backtest_hourly_agent.py:40` imports `db` outright — the one store the backtest deliberately wants. `:177` imports `domain/credits/service.py`, which reaches `credits.repository` (and so `credits_store`) at its own `:27`; `:178` imports `domain/model_providers/service.py`, which reaches `.repository` (and so `model_provider_store`) at its `:38`, and `model_providers/repository.py` imports `database`, `agents/repository.py` and `brokers/repository.py` at its lines 12, 13 and 14. Importing just those two repository modules — `python3 -c "import dashboard.backend.domain.model_providers.repository, dashboard.backend.domain.credits.repository"` — builds **five** of the seven (`db`, `agent_store`, `broker_store`, `model_provider_store`, `credits_store`) with `domain/analytics/service.py` never imported at all. Measured 2026-09-20.
- **The analytics chain, which adds the last two.** Both of those service modules also import `domain/analytics/instrumentation.py` (`credits/service.py:42`, `model_providers/service.py:19`), whose `:15` imports `analytics/service.py`, whose module-level `analytics_service = _build_analytics_service()` (`:253`) builds a value store (`:243` → `build_value_analytics_store`). That store resolves `credits_store`, `model_provider_store`, `agent_store` and `run_store` as **constructor defaults** (`value_repository_postgres.py:79-100`, mirrored at `value_repository.py:342-363`) — but by then the first three are already built, so only `analytics_store` and `run_store` are owed to this route.

Neither route is legible from the child's own import block, which names `db` and two service modules and nothing else; the remaining six are built two to four modules further in, and two of them only as a constructor's default arguments. One new module-level import in the engine's reach adds a payer back, silently, and a guard that must be re-audited on every new import is a guard that drifts. So the scope is every twin that owns a schema — eleven of the twelve pairs in `tests/test_store_twin_parity.py::_TWINS`, verified by grepping `self._init_schema()` across the non-test `*_postgres.py` modules. The twelfth, `PostgresValueAnalyticsStore`, has no `_init_schema` at all: it composes the other stores rather than owning tables, which that file's existing `_NO_OWN_DDL_TWINS` registry already records with a reason. Reuse that registry for the exemption rather than declaring a second one — two owners of one exemption is the disagreement this repo keeps writing rules about. The parent constructs all eleven at import (128 statements), so skipping is safe for every one.

**Both directions print, and the ran-it direction prints its cost.** A skip line alone would leave "the flag reached the child" and "this build has no guard at all" producing the same silence in a log, which is the failure shape this repo's fail-closed-is-not-fail-visible section exists to warn about. And the timing is the only pre-change number the deploy that removes the cost can still produce: the parent runs this same DDL against the same databases at boot and is never a worker, so the parent's boot log *is* the baseline.

**One helper, not eleven copies**, for the reason `db_url.py`'s own header already gives about its credential scrubber ("four hand-copied scrubbers is four chances for one of them to leak"), sharpened by the asymmetry here: an inverted copy fails in the *parent*, where it silently stops running a `CREATE TABLE IF NOT EXISTS` and first surfaces as an `UndefinedTable` on prod from a store nobody edited, while a dropped log line makes "the child skipped DDL" and "this twin was never constructed" the same empty stdout. One condition, one line, one place to read them — and a source-shape test that no non-test `*_postgres.py` still calls `self._init_schema()` directly, so a twelfth twin cannot arrive unguarded.

The SQLite twins are unchanged: their DDL is local and fast, and tests construct them against fresh temp files. **The variable names the process role, not the DDL**, so a human never sets it globally, an older parent that does not set it gets today's behaviour, and future child-only behaviour (turning the analytics snapshot projection off, Track C) has a home.

**Aggregation.** `aggregate_bars` walks every 5-minute source bar with `iterrows` (`bar_aggregation.py:122`), building one `pd.Series` per bar into a per-bucket list (`:120`). **Plain `resample` is not the remedy**, and an earlier draft of this document named it: that module's own header already rules it out (`bar_aggregation.py:10` — it "avoids a plain pandas `resample` because exchange sessions do not begin at midnight and some markets have a lunch break"), and the right-edge bucket labels this module exists to produce are exactly what a midnight-anchored resample cannot give. The change is an **index walk plus a `groupby` on the bucket key**: the per-bucket arithmetic stays byte-for-byte what it was, only how a row finds its bucket moves. It is made **only if** a direct benchmark of `aggregate_bars_by_symbol` on the onboarding shape — 30 symbols × seven sessions of 5-minute bars — exceeds **2.0s**. The gate is on the suspect function alone and not on the surrounding phase, because a phase figure folds in `load_data`'s network time and would let Alpaca's latency argue for rewriting a Python loop. Track A Task 6 Steps 2-4 carry the benchmark, the gate and the change; a change the measurement does not justify is not made.

Everything else in the start — process spawn, the pandas and SDK imports, Neon connection setup, argparse and the handoff — is left alone in this release, but it is **attributed**, not lumped. `starting` stays one phase name (the card has nothing useful to say about spawn versus imports versus stores, and a name the status route must translate is a name the frontend must learn), while its *record* carries three extra keys: `child_entered_at`, `imports_done_at` and `schema_init_seconds`. One run therefore yields four numbers from one phase — spawn plus interpreter, imports including store construction, of which schema DDL, and the preflight remainder. Undo the split and `starting` moves for reasons nobody can attribute, and this release could be credited for a saving it never made. The marks are handed in by the script, which alone can see them, and are **absent rather than zero** when nothing passed them: an unmeasured phase and a free one are different facts, and an engine that read the DDL accumulator for itself would publish the *parent's* boot cost as an in-process run's schema cost. `schema_init_seconds` is the one exception — it is present and `0.0` in a worker, because that zero is the evidence the flag fired.

### Measurement

The phase payload *is* the instrument, and the child's stdout is its durable copy. Locally, one rule-based and one pipeline+LLM run with the OpenRouter and Alpaca keys in `dashboard/.env` record every pre-loop phase and the `starting` split.

Neon DDL and pool setup cannot be measured locally, **and there is no local A/B that would fake it**: with none of the three `*_DATABASE_URL` vars set every store resolves to its SQLite twin, which this release does not guard at all, so toggling `ATL_BACKTEST_WORKER` locally measures exactly `0.00s` and would write a saving that did not happen into the verification table. The local DDL column therefore reads `n/a (sqlite)`, never `0.00`. Nor is the answer a temporary override that re-enables the DDL: that is a second flag whose unset, off and typo'd states are byte-identical, it can be left armed in prod, and it measures a configuration no production run will ever be in. Nor is it a resequenced or separately-shipped Task 5 — neither produces a Neon number locally either.

The pre-change number comes from the **parent's own boot log** on the deploy that ships Track A: same branch, same databases, same Render-to-Neon path, no flag, no sequencing. The parent is never a worker, so it runs every store's DDL and prints **eleven** timed `<store> backend: schema init <n>s` lines — the six that name the stores a child also builds are the round trips the child no longer pays. The `🏊 pg pool created for …` line marks which store's figure carries the cold handshake for its URL. Read against it, the same deploy's child prints **six** `schema init skipped (backtest worker)` lines and a `starting` record whose `schema_init_seconds` is `0.0` — a check that the flag fired in production, not a saving. This is a proxy and is labelled one: the parent boots on a warmed filesystem and the child does not, so the two are comparable in shape, not to the second, and it is a single sample.

## Track B — sampling pinned, recorded, shown

### ⚠ changed: the policy is a per-model table, not a flag

The brainstorm said "models flagged `reasoning` in the catalog". The flag is on **`ProviderCapabilities.reasoning`** (`domain/model_providers/models.py:24`), a per-provider capability, and the execution catalog (`domain/model_providers/execution_catalog.py:28`) is six `CatalogModel(catalog_id, label, vendor)` entries with no per-model capability at all. A provider-level flag cannot say whether *this* model rejects temperature. The policy therefore lives on the catalog entry:

| catalog model | temperature | reasoning_effort | why |
|---|---|---|---|
| `anthropic/claude-haiku-4-5`, `anthropic/claude-sonnet-4-6` | 0 | — | the Anthropic adapter never enables extended thinking, so temperature is accepted |
| `openai/gpt-5.5` | — | `low` | OpenAI reasoning models reject a non-default temperature |
| `google/gemini-3.1-pro-preview` | 0 | — | temperature accepted; the Gemini adapter has no thinking control |
| `deepseek/deepseek-v4-pro`, `qwen/qwen3.7-plus` | 0 | `low` | OpenRouter forwards both; the model ignores temperature while thinking and the effort bound is what tames the ceiling |

`CatalogModel` gains a `sampling: SamplingPolicy` field (`temperature: float | None`, `reasoning_effort: str | None`) with the table above as the values. A model not in the catalog cannot be launched from the dashboard (`preflight_execution_model`, `backtests.py:3080/3099`), so there is no default row.

**The CLI path pins nothing unless it is asked to**, and an earlier draft of this document said the opposite ("defaults to temperature 0"). `--llm-temperature` defaults to `None`, the engine kwarg defaults to `None`, and `request_trading_decision` omits the key when it is unset (`backtest_harness.py:213`: "Temperature is omitted unless explicitly configured"; the guard is `:221-222`), so a run that passes no flag sends byte-identically what it sends today and records `policy: provider_default`. A CLI default of 0 would be a silent request-shape change for every script and cron already invoking this file, and it would delete the *before* arm of Track B's own measurement — that arm **is** an unset temperature. `--llm-reasoning-effort` goes further and is refused outside `--execution-handoff-stdin` (exit 2), because without a handoff the engine builds the plain Anthropic SDK client, which rejects the kwarg; that refusal is deliberately distinguishable by message from the pre-existing one that already stops a bare `--use-llm` on the default pipeline runtime (`backtest_hourly_agent.py:324-328`, "explicit LLM execution requires a signed execution handoff"), since the two refuse the same command for different reasons and only one of them is this design's to relax.

### The wire

The parent resolves the route it already preflights and reads the policy off it (`ExecutionModelRoute` gains the same `sampling` field). The values ride argv: `--llm-temperature 0` and `--llm-reasoning-effort low`, omitted when `None`. They are not secrets and do not belong in the signed handoff envelope. From there:

```
backtest_hourly_agent.main() → HourlyBacktester(llm_temperature=…, llm_reasoning_effort=…)
  → PortfolioManager.make_trading_decision_with_llm(temperature=…, reasoning_effort=…)
    → run_pipeline_decision(…, temperature=…, reasoning_effort=…)      # pipeline branch, :462
      → _create_pipeline_response(…) / _retry_with_recovery_budget(…)  # each value only when not None
        → client.messages.create(…, temperature=…, reasoning_effort=…)
    → _request_trading_decision(…, temperature=…, reasoning_effort=…)  # single-prompt branch, temperature already threaded
      → client.messages.create(…, temperature=…, reasoning_effort=…)   # each value only when not None
```

`_request_trading_decision` is `backtest_harness.request_trading_decision` under an alias (`portfolio_manager.py:55`), so the single-prompt branch reaches the SDK in one hop and does not pass through `_create_pipeline_response` — an earlier draft of this diagram nested it there.

*Only when not None* is load-bearing: the legacy Anthropic SDK client on the CLI path rejects an unknown `reasoning_effort` kwarg. `_retry_with_recovery_budget` carries the same sampling, because it is the same request at a higher ceiling. The single-prompt branch receives the same values, so one policy governs both branches.

**Two values travel, not one object.** The `SamplingPolicy` stops at `ExecutionModelRoute.sampling`: the parent unpacks it there into the two argv flags, and below that the temperature and the effort move as separate keyword arguments the whole way down. So no `sampling=` keyword exists anywhere under the endpoint, and nothing in the script, the engine, the portfolio manager or the pipeline runner has to import the catalog to read a policy — which is also why an unset half can be dropped from a request independently of the other.

### What the adapters do with it

The OpenAI adapter already sends `reasoning_effort` for `openrouter` and `openai_compatible` providers as `extra_body.reasoning` (`adapters/openai.py:115-131`). It gains the native `openai` case, passing `reasoning_effort` as the top-level Chat Completions parameter, gated on the policy so a non-reasoning OpenAI model is never sent it. The Anthropic and Gemini adapters keep ignoring `reasoning_effort`; no catalog row asks them for it. Metadata records what was **requested**; the adapter's filtering rule is documented in code and pinned by tests, not re-recorded per call.

### Persistence and display

The engine writes to `agent_runs.metadata` beside `llm_max_output_tokens` (`engine.py:1052`):

```json
"llm_sampling": {"temperature": 0.0, "reasoning_effort": null, "policy": "pinned_v1", "catalog_id": "anthropic/claude-sonnet-4-6"}
```

`policy` is `"pinned_v1" | "provider_default"`, written per run rather than per deployment. `pinned_v1` means the route carried a `SamplingPolicy` resolved from the catalog, so at least one value was sent. `provider_default` means the run reached a model with no policy on its route — `ExecutionModelRoute.sampling` defaults to `None`, so a route nobody resolved from the catalog claims nothing — and it is **written, not omitted**, because "this run pinned nothing" and "this run predates the field" are different facts and the row says them with different words.

`renderBacktestRunConfig` (`app.js:9700`) adds the Sampling row from this block. Absence of the whole block renders *Not recorded*, following `test_backtest_run_provenance.py`'s rule that an unrecorded field is unknown, not an accusation; a present block with `policy: "provider_default"` renders *Provider default*, which is a statement about the run rather than about the record.

### Proof

A dev script, `dashboard/scripts/diff_backtest_runs.py <run_id_a> <run_id_b>`, prints the first divergent bar, the count of divergent bars and the final-equity gap — and a **`basis`** naming which axis it measured them on. It reads `backtest_decisions` when the runtime wrote one (`basis: "decisions"`, the sharper axis) and otherwise falls back to the equity curve, which every run writes (`basis: "equity"`).

**For everything in this design's scope the basis is always `equity`, and that is not a degradation to note in passing — it is the only axis that exists here.** `run_agent_backtest` calls `db.insert_decisions` only on the AI Hedge Fund runtime (`engine.py:1774-1775`), so a `runtime_type="pipeline"` run — the runtime this document scopes itself to in its second line — writes no `backtest_decisions` rows at all. A decision-level diff of two such runs is not a weaker measurement; it is not a measurement. The decision fields therefore come back **`None`, never `0`**: a zero divergence count read off an empty table is the one claim this script must never make by accident, and `0` is exactly what it would say. `basis` is the shared word — the same key the script emits and the same column the plan's result table carries — so a reader of either can tell which number they are holding without inferring it from the runtime.

Verification runs one configuration three times before Track B and three times after, locally, and the plan's final section records the table with its `basis` column. Every row should read `basis: equity`; a row reading `basis: decisions` means the runtime changed underneath the measurement and the number is not comparable with the others. The expected outcome is *later and smaller* divergence, not zero.

## Failure behaviour

- **Progress write fails.** Logged, never fatal, exactly as `_publish_live_progress` behaves today (`engine.py:641`).
- **Child sees `ATL_BACKTEST_WORKER` but the schema is missing.** Impossible from a parent that imported the stores, and a stale image gets a loud psycopg error on the first query, which fails the run visibly. Accepted.
- **The engine has no progress file.** The phase *clock* still advances: `_publish_live_progress` moves the state machine before its `if not self.progress_file: return` (`engine.py:590`), not after. Below that return an engine with no progress file — every CLI run, the external-run session, the algo service — would never leave `first_decision`, and the next transition would close a `first_decision` spanning the entire bar loop: the one number this phase exists to produce, "how long until the first model decision?", published as hours instead of seconds, on the path where the stdout line is the only reader there is.
- **A startup mark the script did not pass.** The key is absent from the `starting` record, not present at `0.0`, and the measurement reader prints `MISSING` for it. A zero-duration figure and an unmeasured one are different facts; a table that renders them the same is the same failure as not reporting at all. `schema_init_seconds` is deliberately the exception — `0.0` there is a measurement.
- **A provider rejects the pinned parameter.** The call fails as a provider error, the run fails visibly with the provider's message, and `llm_sampling` in metadata shows which rule caused it. The pairing is pinned where it is decided rather than enumerated: a catalog test fixes the policy table row by row, and an adapter test pins that the native `openai` case sends `reasoning_effort` only when the policy asks for it — while `adapters/anthropic.py` and `adapters/gemini.py` never read the field at all (`grep -n reasoning_effort` over both returns nothing) and no catalog row asks them for it. A "every catalog row × every adapter it can reach" table was considered and is not written, because that set is not a property of a catalog row: `_provider_model_id` (`execution_catalog.py:60-77`) decides routability from the *provider record*, and its `openai_compatible` arm reads that provider's `model_allowlist`, so the table would enumerate deployments rather than rows and could never be exhaustive.
- **`reasoning_effort` requested of an adapter that ignores it.** Nothing is sent; metadata says *requested*, the card renders whichever pinned shape the record has (*Pinned · reasoning effort low (no temperature sent)* or *Pinned · temperature 0 · reasoning effort low*), and the adapter rule is where the truth lives. No catalog row currently triggers this.

## Sequencing
