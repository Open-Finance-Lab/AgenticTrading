1What this is & where it sits 定位

The guidance fixed the destination (six-plane 自动化托管平台, five objects, six contracts, roadmap gates). The blueprint fixed the materials ($0 on-ramps: DBOS, pgmq, Neon, R2, DuckDB, gVisor, Inspect AI). This document fixes the work order: the concrete, sequenced steps that take today's repo to (a) an in-house fleet of LLM agents continuously backtesting and paper-trading on ATL, and (b) a community on-ramp where outside builders test their own agents and strategies — the funnel that feeds the ≥50-submission demand gate.

先闭环，再扩展，再展示。
Close one real loop before widening; widen before displaying. The fleet closes the loop and stress-tests the rails; the community widens it; the leaderboard and Agent Cards display it. Every step below lands as a platform asset under one of the six contracts — no contract, no platform asset.

Two structural insights drive the sequencing:

  • The backtest fleet is nearly free; the paper fleet is a real build. External agents can already register, get an API key, and drive a full backtest step-by-step through /api/v2 (scopes, rate limits, idempotency, run caps, reaper, restart recovery — all shipped). Paper trading, by contrast, has zero execution code: the entire /paper/* surface is a read-only display proxy over one shared Alpaca account, and execution/paper_backend.py is a stub whose own spec says it "requires a focused design pass." So the fleet starts trading this week on the backtest rail while Phase B is designed properly.
  • Persistence-first is the forced move. Run history lives in ephemeral SQLite (issue #140): every deploy erases every run, decision log, and leaderboard entry. That same ephemerality is why nothing can be scheduled (issue #145: an off-instance cron writes to its own dead copy of the DB). Moving runs to the dedicated Neon project (blueprint §5) makes prod state reachable from anywhere — at which point a $0 GitHub Actions cron discharges #145 and the fleet has a heartbeat.

Why this inventory matters

The gap is asymmetric. Backtesting has a complete, hardened agent-facing rail with unified lifecycle infrastructure that is backend-agnostic (the reaper, heartbeats, caps, and tombstone recovery drive any ExecutionBackend generically). Paper trading has pure domain logic waiting to be composed but no broker write path, no cadence driver, no per-agent isolation, and no integrity guard. The plan therefore ships the fleet on backtests immediately (Track A) and treats paper as a designed build (Track B) — not the other way around.

3The three constraints that shape the design 约束

3.1 Alpaca: 3 paper accounts per login — the fleet cannot be "one real account per agent"

  • Standard (non-Broker-API) users: max 3 simultaneous paper accounts per loginⁱ (Alpaca staff, community forum, 2026-03); reset is now delete-then-recreate with fresh keys; multi-paper expansion is roadmap-only, no date. Beyond 3, the only sanctioned path is Broker API — a business-tier product, per Alpaca's own OAuth-vs-Broker-API guidance the wrong tier for ATL now (blueprint §1).
  • Trading API: 200 requests/min per account, ~10/s burstⁱ. Market data free tier: IEX feed, 200 req/minⁱ; websocket 1 connection, 30 trade/quote channels (minute bars uncapped)ⁱ — the DJIA-30 universe fits exactly. SIP + 10k req/min is the $99/mo Algo Trader Plus tier — a scale trigger, not a Week-0 need.
  • No ToS prohibition on bot trading found; Alpaca's whole positioning is agent-first (the 2026-07-16 $135M raise explicitly for "agent-first brokerage infrastructure" ✓; monthly active API users ~4× in 6 monthsᵛ). Their official OSS MCP server (65 tools, paper-by-default) ships no execution guardrails — validation that ATL's trust-gated layer is the differentiator, not a commodity.
  • Design analog: QuantConnect scopes paper trading per-project ($100k simulated capital per deployment), sidestepping any account-count ceiling — the shape ATL should imitate.

3.2 Render free tier: web-only, ephemeral, sleeps

  • Live prod is free-tier: one type: web service, no persistent disk, no cron/worker, cold-starts after idle (render.yaml's standard plan + disk are aspirational). Any in-process interval loop dies when the dyno sleeps; any off-instance scheduler writes to its own ephemeral DB copy, never prod's.
  • Consequence: durable-Postgres-first, then schedule from outside. Once runs live in Neon, a GitHub Actions cron (already-proven CI secrets + deploy-hook pattern, PR #95) reaches prod state at $0. In-service scheduling arrives later via the DBOS spike (blueprint Week 1–2), whose Neon CU-burn measurement decides where the workflow engine's system DB lives.

3.3 MCP 2026-07-28: the largest spec revision since launch, 8 days out

  • Stateless core, Tasks-as-extension, SDK v2 renames to MCPServer — breaking against the repo's pinned mcp==1.23.0. Standing rule from the blueprint, carried verbatim: hold all new MCP server code until the final spec lands; anything built this week is born legacy. Phase C (the MCP façade over v2) stays mechanical-when-ready — every v2 endpoint is already MCP-shaped.

4Six load-bearing decisions D1–D6

The 14-agent sweep surfaced five genuine contradictions or gaps that block a coherent plan. Each becomes an explicit decision below — four are engineering calls this document makes and defends; two (D1 sign-off, D6 incentives) need human sign-off beyond it.

D1 · Run history moves to the dedicated Neon runs project needs user + lab sign-off
Issue #140 lists three options (Postgres / paid disk / accept split). The blueprint already selected and detailed option 1 at $0 (own Neon project = own free allotment; R2 trace_ref blobs; #134 twin pattern with the #135 ALTER lesson) — but the issue itself is still formally open. This plan treats D1 as its first step because everything else stands on it: durable runs, schedulable refreshes, community run history, Trace-as-asset.
Unlocks: #140 and #145 · Scope note: port agent_runs + equity + trades + decisions + manifests + idempotency and protocol_runs/steps (the v1+v2 ledger) — the hottest tables; WAL-sidecar and lazy-ALTER traps apply.
D2 · Virtual portfolios for the fleet; ≤3 real Alpaca paper accounts for hero agents this doc's call
A fleet of N agents + an open community cannot map 1:1 onto real Alpaca paper accounts (cap = 3ⁱ). So: every fleet/community agent gets an ATL virtual paper portfolio — per-agent cash/positions/fills ledger in the runs DB, fills simulated at live IEX quotes by the already-extracted pure execute_actions(), one shared market-data feed for everyone (QuantConnect's per-project model, ATL-flavored). The ≤3 real accounts are reserved for showcase "hero" agents — including the guidance's 8-K hero-milestone loop — where Alpaca's own fill simulation adds realism and credibility.
Bonus: the virtual ledger's commit point is exactly where Trust-boundary v0 belongs — one gate, both paths (virtual fill or real paper order). Broker API calls stay near-zero regardless of fleet size.
D3 · The in-house fleet dogfoods /api/v2 — same rail as the community this doc's call
Today's 7 entries run through the internal llm_agent strategy path; external agents use v2. Growing two parallel rails violates 统一行动原则. Going forward the fleet registers as first-class v2 agents (Agent Identity + Manifest + API key), driving runs through the same protocol the community uses — every fleet run produces a Trace, exercises the contracts, and finds community-facing bugs before the community does. The internal replay path remains for baselines and for the H6-gated daily-board refresh until leaderboard sourcing is generalized (Track B step 9).
Honest note: leaderboard identity today joins on llm_model ↔ config strategy id, write-once per window — v2-sourced entries need the Evaluator-API generalization; don't hack it early.
D4 · Scheduling: GitHub Actions cron now, DBOS after the spike this doc's call
Phase 1 (post-D1): a scheduled GH Actions workflow runs the daily refresh + fleet backtests against Neon — $0, no new infra, discharges #145. Phase 2: the blueprint's DBOS spike (Week 1–2, wrapping exactly this refresh workflow as its first consumer) measures Neon CU-burn and, if green, becomes the durable in-service driver — mandatory for paper trading's wall-clock cadence, which a 6-hourly GH cron cannot provide. The Discord-bot worker (~$7/mo) is the proven fallback if an always-on process is needed before DBOS concludes.
Sequencing: GH cron is an interim addition to the blueprint, not a replacement — DBOS remains the committed direction.
D5 · H6 extends to the paper path before any paper result is published this doc's call
The H6 integrity guard exists only on the backtest/leaderboard path; domain/trading has zero LLM instrumentation. Verified: the guard reads used_llm/llm_decisions/decision_steps by duck-typing — a paper decision loop that carries the same counters passes through unchanged. Paper runs additionally need windowed coverage (an open-ended session shouldn't be permanently tainted by one bad patch). No paper equity curve reaches the leaderboard without clearing the same ≥95% bar.
Why it matters: "the model actually drove it" is the platform's credibility asset — the Evaluator-API/trajectory-eval first the blueprint names (H6 is the seed).
D6 · Community incentives: flagged open, not decided here lab decision
The guidance leaves cold-start mechanics (Numerai-style staking vs Alpha-Streams-style revenue share vs none) explicitly open. Track C builds everything that doesn't depend on it: frictionless onboarding, Agent Cards, contest wiring into the FinRL Contest community (85 teams in 2025, verified), a visible submissions counter against the ≥50 demand gate. The incentive choice goes to the lab with the contest proposal (3–9 mo window) — it does not block Weeks 0–4.
Also open: SDK versioning erratum — 0.2.0 shipped v1-only despite the stated v2 gate; the v2 release becomes 0.3.0 (record it, don't relitigate it).

6The plan — four tracks, every step 分轨计划

Track P0 · Platform rails 平台底座 Week 0–1

  1. P0.1 — Sign off D1 (user + lab, on issue #140): runs move to the dedicated Neon project. One message, three options already framed in the issue; the blueprint's $0 resolution is the recommendation. Everything below assumes yes.
  2. P0.2 — Runs-to-Postgres migration. Apply the #134 store-factory + *_postgres.py twin pattern to the run tables: agent_runs, equity_timeseries, trades, backtest_decisions, run_manifest, idempotency_keys, and protocol_runs/steps. New env var (e.g. RUNS_DATABASE_URL) with startup backend logging exactly like #134's; lazy-ALTER migration path from day one (#135 lesson); never touch the seed DB in place (WAL-sidecar trap); conftest.py strips the env so tests stay on SQLite. Incremental equity appends (paper needs append semantics, not write-once curves) enter the schema here. This is the largest single work item in the plan — treat it as its own spec.
  3. P0.3 — Contracts v0 (discharges queue task atl-platform-contracts-01): six Pydantic models + exported JSON Schemas in dashboard/backend/contracts/, formalizing existing seeds — external_agents→Agent Manifest, v2 lifecycle→Runner API, run_manifest(+trace_ref)→Trace Schema, leaderboard service→Evaluator API, Agent Card aligned to A2A's signed-card shape, Tool Manifest deferred to post-Jul-28 MCP shapes. Mechanical formalization, not design.
  4. P0.4 — Wire Logfire (one-line FastAPI auto-instrument, free 10M spans/mo): ends the "logging is invisible in prod" era before the fleet starts generating load worth observing.
  5. P0.5 — Phase B design spec (the "focused design pass" the v2 spec explicitly demands): PaperBackend realtime loop, order-capable Alpaca adapter, D2 virtual-portfolio ledger schema, cadence + decision-window semantics, non-terminal restart re-attachment (the tombstone pattern covers finished runs, not resuming live ones — Alpaca/ledger is the source of truth on restart), D5 windowed H6 counters, Trust-boundary v0 check list and ordering. Written and reviewed this week so Track B starts Week 2 with no design debt.
  6. P0.6 — Funnel quick-fix PR batch (small, independent, immediate): fix SDK repo links (Allan-Feng → Open-Finance-Lab); fix-or-delete the broken POST /paper/start-session; triage frontend/SDK robustness issues #151/#152/#153/#154 into the normal flow.

Track A · Backtest fleet 回测舰队 Week 1–2 · the loop closes here

  1. A.1 — Schedule the daily refresh (discharges #145): GH Actions cron runs refresh_daily_leaderboard.py --models against Neon with CI-stored keys (secrets precedent exists since the PR #95 deploy hook). Daily-board LLM entries appear in prod for the first time, and survive deploys. H6 stays the publication gate.
  2. A.2 — Register the fleet as v2 agents (D3): each in-house model gets an Agent Identity + Manifest + key. A thin fleet-driver script (same cron) walks each agent through a daily-window v2 backtest via the protocol — dogfooding the exact community path, producing Traces, and continuously exercising caps/rate-limits/idempotency under real load.
  3. A.3 — Cost telemetry rollup: per-run est_cost_usd already lands in the runs DB (now durable) — add a trivial DuckDB/SQL weekly rollup so fleet spend is a number, not a feeling, before scaling N.
  4. A.4 — DBOS spike (blueprint Week 1–2, unchanged): wrap exactly one workflow — this refresh — in DBOS Transact; measure the Neon CU-burn question (~0.25 CU always-on ≈ 180 CU-hr/mo vs the 100 free); outcome decides the Phase-2 driver home (tune polling / separate Neon project / pilot box local PG). Decorator code is identical in all three outcomes.

Track B · Paper fleet 纸面交易舰队 Week 2–4 · the real build

  1. B.1 — Adopt the Phase B spec (from P0.5) after review.
  2. B.2 — Order-capable Alpaca adapter: add POST /v2/orders submission, fill-status polling (paper fills aren't instant), and rejection/error mapping beside the existing read-only client. Alpaca's own MCP server is the reference for call shapes — read it, don't adopt it (no guardrails; MCP code is frozen till Jul 28 anyway).
  3. B.3 — Virtual portfolio ledger (D2): per-agent cash/positions/fills persisted in the runs DB; fills simulated at live IEX quotes via the pure, already-tested execute_actions(); one shared market-data fetch per cycle serves every agent (30-symbol universe = one bars call — rate limits become a non-issue); cache keys namespaced per agent/run.
  4. B.4 — PaperBackend implements ExecutionBackend: realtime loop with hourly bar-close cadence — a decision window opens per cycle, late/absent decisions HOLD (mirroring backtest semantics, per-cycle rather than blocking). Plugs into the existing reaper/heartbeat/cap machinery unchanged; adds its own non-terminal restart re-attachment (rebuild from ledger + Alpaca truth, not from a tombstone).
  5. B.5 — Trust/Commit boundary v0 (the guidance's one BUILD item, landing exactly where the blueprint said it would): structured Action Intent (validator.py, unchanged as the hard JSON-only wall) → 7 config-declared deterministic checks (cribbing NautilusTrader RiskEngine / LEAN buying-power + brokerage models / vn.py throttling) → per-agent budget/permissions → execute (virtual fill or real paper order) → receipt + reconciliation. Audit-log every allow and every deny. One gate, both execution paths.
  6. B.6 — H6 for paper (D5): the paper decision loop carries used_llm/llm_decisions/decision_steps (duck-type compatible with the existing guard, verified), windowed for open-ended sessions. No paper curve is published below the bar.
  7. B.7 — Unlock mode: "paper" in v2: drop the ^backtest$ regex, add paper-appropriate run caps and scope checks. The community can now request paper runs on the same contract as backtests.
  8. B.8 — Hero agents on real Alpaca paper (≤3 accounts): the showcase tier, including the guidance's hero-milestone slice — 8-K event (EDGAR poll → pgmq table, EventRadar v0) → FinSearch retrieval → decision → Trust checks → real Alpaca paper order → trace row + R2 blob → leaderboard. Thin at every stage; end-to-end beats deep.
  9. B.9 — Paper leaderboard surface: new session naming (e.g. leaderboard-paper) + incremental equity appends + live H6 coverage; generalize entry sourcing enough that v2-driven runs can publish (the Evaluator-API seam). The frontend Paper Trading tab becomes per-agent (virtual portfolios + hero accounts) instead of one shared account view — and /paper/* gets auth/ownership before any community-facing write path exists.

Track C · Community on-ramp 社区入口 Week 3–4 · feeds the ≥50 demand gate

  1. C.1 — SDK 0.3.0 on v2: migrate agentictrading to the v2 contract (the one open build task from the platform adoption), correct repo links (P0.6), publish. v1 stays frozen-but-working for existing integrations.
  2. C.2 — Docs that match reality: a v2-first quickstart (signup → register → key → first backtest → see yourself on the board in <15 minutes), v1 explicitly marked "compatibility surface", paper-mode docs when B.7 lands, onboarding walkthrough for non-SDK users. Fix the RTD rebuild pipeline (site last built 2026-05-11 — new docs literally cannot render). All user-facing doc edits are Felix-coordinated (§10 lists every stale item found).
  3. C.3 — Agent Cards MVP: registry + leaderboard join, A2A-exportable shape (contracts from P0.3); every community agent gets a public face — purpose, limits, performance, risks, provenance.
  4. C.4 — Contest onboarding: wire the seasonal-lab framing to the FinRL Contest community (85 teams in 2025, verified — the cold-start engine); a visible submissions counter against the ≥50 demand gate; contest outputs land as platform assets, not slide decks. Incentive mechanics (D6) go to the lab as a proposal alongside this.
  5. C.5 — Discord parity: external/SDK-registered agents become selectable in /agent; fix the deep-link ownership bug (#151) and API timeouts (#152). Discord is the community's lowest-friction front door — it should see the same agent population as the web.
  6. C.6 — Security boundary, stated and kept: community code never executes on ATL infrastructure in this phase — agents run on their owners' machines and speak the API/SDK. Server-side hosted community agents wait for the sandbox tier (gVisor spike → Daytona/E2B), per the blueprint's execution-plane sequencing. Prompt-injection defense is sandbox-hard, never prompt-soft.
